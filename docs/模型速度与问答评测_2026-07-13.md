# Model QA Report - llama.cpp b9982 推理速度回归诊断

## Executive Summary
**对象**: 本机 GTX 1060 6GB (Pascal, sm_61) 上部署的 llama.cpp 二进制
**二进制**: b9982 (commit 99f3dc322, Clang 20.1.8) 对比 b9957 (7-12 真机基线)
**QA 类型**: 触发式（用户报告"今天部署的模型普遍速度降低 30%+")
**总体结论**: **Sound with Findings** — 二进制本身未损坏，但 b9982 在 Pascal 上改变了 `--flash-attn auto` 的行为，导致使用 `auto` 的主力模型 TG 解码速度掉 39~44%；使用显式 `on` 的模型不受影响。

## 根因分析

**观察**: 所有带 `--flash-attn on`（显式强制）的模型速度正常甚至快（36/25/45 t/s）；所有带 `--flash-attn auto` 的主力模型（4B/35B）TG 掉 ~40%。同一台机器、同一套参数（`auto` + `q8_0`/`q4_0` KV + `ngram-mod`），**唯一变量是二进制版本 b9957→b9982**。

**证据**:
- PP（prompt 处理）速度正常（309–486 t/s），只有 TG（逐 token 解码）掉 → 教科书级"Flash Attention 被静默关闭"指纹（FA 只影响解码段 attention，且长上下文 KV 解量化在无 FA 时走慢路径）。
- ngram 投机解码在 auto 组"在"但不顶用 → 印证惩罚来自 FA→非FA 的解码路径，而非 spec 失效。
- `on` 组在 b9982 上跑出正常速度 → **证明该构建在 Pascal 上 FA kernel 是可用的**，只是 `auto` 判定不再选择它。

**结论**: b9982 (commit 99f3dc322) 在 Pascal sm_61 上把 `--flash-attn auto` 解析为"不启用 FA"（b9957 会启用）。这是本次"普遍变慢"的唯一系统性根因。

> 注：b9982 已不再打印 `flash_attn =` 状态行，无法直接读开关；但 on/auto 对照实验已是最强因果证据。

## 排除项

- **14:47 两次启动即退**: 两个 `_console.log` 仅含 BUILD INFO 头、无 runtime 输出，为端口 8081 被上一进程占用导致的快速重启冲突，与速度无关（Info 级）。
- **DLL 错配**: 已整包替换 b9982（日志 build 指纹一致 = 9982），排除。
- **掉回 CPU**: 日志 `n_gpu_layers` 均按配置上 GPU（99/64/60），排除。

---

## 修复建议（Finding 1）

将以下 3 个主力模型的 `--flash-attn auto` 改为 `--flash-attn enabled`：
1. Qwen3-4B-Instruct (32K, q8_0 KV)
2. Qwen3.5-4B Thinking (48K, q4_0 KV, --reasoning on)
3. Qwen3.6-35B MoE (32K, q4_0 KV, cpu-moe)

**预期**: 4B 回到 ~30+ t/s，35B 回到 ~13 t/s（对齐 b9957 基线）。
**风险**: 零。若某模型 `enabled` 构建期报错（说明该构建真未编 Pascal FA kernel），唯一正解是回退 b9957。
**`on` 组无需改动**（已显式强制，速度正常）。
